# 智能体中台的四层架构取舍策略
核心结论先给透：**智能体中台绝对不是选某一层，而是「L3 做核心骨架打底，L1/L2 做普惠主力，L4 做高阶增值按需开通」——一套内核、分层输出、智能路由、按需降级**。

中台的本质诉求是「一套底座支撑多业务/多租户，兼顾管控合规、能力复用、成本可控」，绝不能为了技术先进性全量上 L4，也不能只做 L1/L2 撑不起复杂 B 端需求。最优解是架构内核按最高标准搭建，业务调用按最低成本匹配。

## 一、中台取舍的核心底层逻辑
先明确中台和单业务系统的本质差异，这是所有取舍的出发点：
1. **复用优先**：能力一次开发，多业务线/多租户反复调用，不能每个业务各搞一套
2. **管控刚性**：必须统一租户隔离、权限、审计、计费、合规留痕，不能失控
3. **成本敏感**：80% 的请求是简单场景，不能用复杂架构去承接，否则成本直接翻倍
4. **弹性扩展**：既要能支撑 C 端轻量化问答，也要能支撑 B 端复杂多领域协同

基于这四点，四层架构在中台里不是四选一，而是**分层共存、向下兼容、智能路由**：同一个内核框架，通过配置开关控制启用的能力层级，简单请求走短链路，复杂请求自动升级。

## 二、四层架构在中台里的定位与取舍
### L1：纯 ReAct 单智能体 —— 基础普惠层，必做、薄做
**中台定位**：原子级基础能力，全量默认开放，承接 60%~70% 的简单请求
- **必做理由**：绝大多数 C 端问答、单工具调用、简单查询，用 L1 就足够，链路最短、延迟最低、token 消耗最少，是成本控制的核心
- **怎么取舍**：
  - 只做标准化能力：统一工具网关接入、统一风控审核、统一计费埋点，不做定制化
  - 作为所有高阶架构的基础单元：L2 的 SubAgent、L3 的 Executor，内部本质都是 L1 规格的 ReAct 智能体
  - 投入占比低：约 10% 的研发精力，把基础能力做稳即可，不用深度优化

**承接场景**：C 端普通对话、单步工具调用、简单信息检索、租户自定义的轻量 Bot

### L2：ReAct + SubAgent 工具化 —— 标准主力层，重点做、做厚
**中台定位**：业务级能力封装层，中台核心复用单元，承接 20%~25% 的中等复杂度需求
- **必做理由**：这是中台「能力沉淀、复用降本」的核心载体。把行业能力（财务、法务、运维、客服）封装成标准化 SubAgent 工具，所有业务线/租户直接调用，不用重复开发
- **怎么取舍**：
  - 重点建设「SubAgent 能力市场」：统一封装规范、统一入参出参标准、统一验收规则，支持租户按需订阅
  - 主 Agent 保持轻量化：只做调度和结果整合，不承载复杂逻辑，避免上下文膨胀
  - 投入占比中等：约 30% 的研发精力，核心做标准化封装、质量管控、可复用性

**承接场景**：普通 B 端租户业务、单领域多步骤任务、对话中穿插专项能力（如客服对话中调用退款计算 SubAgent）

### L3：Planner + Executor 主从架构 —— 核心骨架层，必须做深做透
**中台定位**：中台的管控中枢与架构骨架，承接 5%~10% 的长流程、强管控需求
- **必须做深的核心理由**：
  1. **管控刚需**：只有规划与执行分离，才能实现全链路审计、任务可追溯、结果可验收，满足 B 端企业合规诉求
  2. **目标对齐**：长周期任务必须靠全局 Planner 锚定目标，避免 L2 边想边干导致的目标漂移
  3. **中台骨架**：租户隔离、权限管控、计费统计、任务调度，全部依附在这一层的 DAG 任务体系上
- **怎么取舍**：
  - Planner 做「强规划、弱干预」：一次性输出全局任务图谱，只在触发明确阈值时才重规划，绝不每步都介入，避免成为性能瓶颈
  - Executor 标准化：每个 Executor 直接复用 L2 的 ReAct+SubAgent 能力，不重复造轮子
  - 重点建设共享状态池、任务调度引擎、全链路埋点，这是中台的基础设施
  - 投入占比最高：约 40% 的研发精力，是整个中台的稳定性基石

**承接场景**：中大型 B 端租户、长流程工单、报表生成、批量任务、强合规审计场景、BC 端核心业务流水线

### L4：中心化混合架构（可横向通信 Executor 集群）—— 高阶增值层，按需开通、强约束做
**中台定位**：大客户专属高阶能力，仅面向付费企业客户/核心业务线开通，承接 <5% 的极致复杂场景
- **不做全量开放的理由**：
  1. 架构复杂度指数级上升，调试、排障、运维成本极高，全量开放会拖垮整个中台的稳定性
  2. 横向通信会带来 token 消耗上升、结果不可控风险，普通租户用不上也承担不起成本
  3. 95% 的业务场景，L3 已经完全能满足，不需要横向协同
- **怎么取舍（核心是「受限」二字）**：
  - 坚决不做开放式自由对话：横向通信仅限**预设结构化接口**，固定入参出参、最大交互轮次（≤3 轮）、超时强制熔断
  - 白名单开通：仅给付费大客户、内部核心业务线开放，普通租户默认关闭
  - 只做仲裁不做博弈：平级 Agent 只能做数据查询、参数对齐类协作，冲突和决策必须上报顶层 Planner 仲裁
  - 投入占比可控：约 20% 的研发精力，重点做通信协议、冲突仲裁、熔断降级、隔离部署，不追求极致灵活性

**承接场景**：大型企业跨部门复杂协同、多领域深度联合任务、全栈研发 Agent、工业级故障排查等高价值场景

## 三、中台落地的 5 条核心取舍原则
### 1. 底座一套，能力分层，坚决不做四套独立架构
不要分别开发 L1/L2/L3/L4 四套系统，而是**同一个内核框架，通过开关控制能力层级**：
- 同一个 Executor，关闭推理就是 L1 Worker，开启 ReAct+SubAgent 就是 L2，开启横向通信接口就是 L4 协同节点
- 同一个 Planner，关闭重规划就是纯一次性规划，开启触发式重规划就是 L3，开启冲突仲裁就是 L4 顶层中枢
- 好处：研发成本最低、能力复用率最高、运维口径统一

### 2. 管控能力前置，协同能力后置
中台的优先级：
**租户隔离 > 权限管控 > 审计计费 > 规划执行 > 工具能力 > 横向协同**
先把 L3 的管控骨架做扎实，再谈 L4 的协同灵活性；管控是中台的生命线，协同只是增值项。
反过来，如果一开始就主攻 L4 平级协同，很快就会陷入「效果不可控、排障难、成本失控、合规不达标」的困境。

### 3. 默认降级，主动升级，成本最优
接入网关做智能路由，默认走最低层级，满足不了再自动升级：
1. 简单问答/单工具调用 → 直接走 L1 短链路
2. 单领域多步骤 → 升级 L2
3. 长流程多角色、需要目标对齐 → 升级 L3
4. 明确跨领域高频交互 → 白名单内升级 L4
**核心目标**：用最低的架构成本、最少的 token 消耗，满足业务需求，而不是一味追求架构高级。

### 4. L4 必须做物理/逻辑隔离，不能和普惠链路混部
- 大客户的 L4 协同任务，优先走独立算力池、独立 Agent 实例，避免复杂任务抢占普通业务资源
- 横向通信日志单独存储、单独审计，和普通任务链路隔离，降低排障和合规风险

### 5. 能力下沉，业务变薄
中台越做越厚，业务越做越薄：
- 把通用的规划、调度、工具、审计、权限全部下沉到中台底座
- 业务侧只需要配置业务规则、接入私有数据、定义业务流程，不用关心底层架构是 L2 还是 L3

## 四、典型中台落地配比参考
| 层级 | 业务请求占比 | 研发投入占比 | 面向客群 |
| :--- | :--- | :--- | :--- |
| L1 纯 ReAct | 60%~70% | 10% | C 端大众用户、轻量租户 |
| L2 ReAct+SubAgent | 20%~25% | 30% | 中小 B 端租户、标准业务线 |
| L3 Planner+Executor | 5%~10% | 40% | 中大型 B 端租户、核心业务线 |
| L4 受限混合架构 | <5% | 20% | 头部付费大客户、战略级业务 |

## 最终总结
智能体中台的最优架构路径不是选某一层，而是：
**以 L3 规划执行分离为核心骨架，以 L2 SubAgent 工具化为核心复用单元，以 L1 为普惠基础能力，以 L4 受限协同为高阶增值选项**。

简单说就是：底座按 L3 建，能力按 L2 沉淀，普惠用 L1 承接，大客户按需开 L4。既保证了中台的管控性与复用性，又兼顾了成本与灵活性，是当前业界智能体中台的共识落地方案。

编码场景是典型的**长链路、强纠错、易目标漂移**场景，选型严格匹配任务复杂度，和你梳理的四层架构完全对应：**日常编码主力用 L2，项目级复杂开发上 L3，只有团队级多角色协同才需要 L4，纯 L1 只适配最轻量的补全修复**。

下面对应每一层讲清楚适用边界、内部逻辑和落地现状。

## 各层级编码场景适配详解
### L1 纯 ReAct 单智能体：仅适用于极轻量编码
**适用任务**：3步以内的极简操作，比如单行语法修复、单函数生成、简单脚本编写、单条命令执行、单处代码格式化。
- 特点：任务边界清晰，不需要管理多文件上下文，不需要全局目标对齐
- 示例：“给这个函数加个非空校验”“写一个 Python 读取 CSV 的脚本”“修复这个语法报错”

**为什么只用 L1**：步骤极短，单 ReAct 闭环（思考→改代码→执行验证）链路最短、延迟最低、token 消耗最少，分层反而徒增 overhead。

**核心局限**：文件数量超过 2-3 个、步骤超过 5 步后，极易出现上下文爆炸、目标漂移——改着改着就忘了最初的需求，或者顾此失彼破坏了其他逻辑。

### L2 ReAct 主 Agent + SubAgent 工具化：日常编码的绝对主力
这是 80% 单人日常开发场景的最优解，也是 Cursor Agent、Claude Code 等主流编码产品的默认架构。
**适用任务**：单文件/单模块功能开发、局部代码重构、单 Bug 排查修复、单接口联调、带测试验证的功能实现。

**内部编码逻辑**：
- 主 Agent 把控整体修改目标，跑核心 ReAct 循环：分析需求→修改代码→验证结果→迭代纠错
- 将「跑单元测试、执行终端命令、查依赖文档、Git 提交、代码格式化、静态扫描」这类重复专项操作，封装成 SubAgent/黑盒工具
- 主 Agent 不感知子任务执行细节，只接收最终结果（比如测试是否通过、报错信息是什么），大幅降低自身上下文压力

**为什么是日常主力**：
既保留了单 Agent 的灵活度，又通过 SubAgent 剥离了机械重复的执行操作，控制了主节点上下文膨胀，完全能覆盖绝大多数单人开发需求，且调试成本低、效果可控。

### L3 Planner + Executor 主从架构：项目级复杂编码的标配
这是解决「长编码任务目标漂移」的核心方案，也是企业级研发 Agent 的标准骨架（如 Devin、大厂内部代码开发 Agent）。
**适用任务**：多文件功能开发、全栈单功能实现（前端页面+后端接口+数据库）、中型项目重构、完整需求从 0 到 1 开发、跨模块 Bug 排查。

**内部编码逻辑**：
- **Planner（架构师角色）**：开头一次性做全局需求拆解，输出结构化开发计划：
  1. 设计数据库表结构
  2. 编写后端实体类与接口
  3. 编写前端页面组件
  4. 编写单元测试用例
  5. 全链路联调验证
  明确每个子任务的目标、文件范围、验收标准，全程锚定整体需求，防止跑偏。
- **每个 Executor（开发工程师角色）**：就是一个完整的 L2 规格智能体（ReAct+SubAgent），只负责单个子任务（比如只写后端接口），内部自己读文件、写代码、调试验证，完成后返回结构化结果。
- Planner 最终做整体校验、逻辑整合，结果不达标则触发局部重规划。

**为什么这个场景必须 L3**：
编码任务越长、涉及文件越多，纯 L2 越容易出现“写着写着偏离原始需求”“改了A模块忘了B模块的约定”的目标漂移问题。Planner 一次性锚定全局方案与接口约定，每个 Executor 专注自身模块，是目前解决长编码任务稳定性的最有效方案。

### L4 中心化混合架构（Executor 可横向通信）：团队级协同的高阶选项
属于大客户增值能力，普通中小项目完全用不上。
**适用任务**：大型项目多模块并行开发、团队级全栈协作（前端 Agent+后端 Agent+测试 Agent+安全审计 Agent+DBA Agent）、跨团队代码评审联调、复杂系统故障排查。

**内部编码逻辑**：
- 顶层 Planner（技术负责人角色）：定整体架构、接口规范、开发排期、验收标准，分发任务，负责最终仲裁
- 中层各领域 Executor：每个都是 L2 规格，各自负责专属模块，同时开放**受限横向通信**：
  - 后端 Agent 写完接口，直接把结构化接口定义同步给前端 Agent，前端直接对接开发
  - 测试 Agent 发现 Bug，直接把 Bug 单同步给对应开发 Agent 修复
  - 安全 Agent 扫描出风险，直接把修复建议同步给开发 Agent
- 只有出现接口争议、方案冲突、进度异常时，才上报顶层 Planner 仲裁，常规交互不占用主节点算力

**为什么需要横向通信**：
如果全走 Planner 中转，前后端联调、测试提 Bug、代码评审这类高频交互会非常低效，平级直接传递结构化信息，效率提升非常明显。但必须强约束：禁止开放式对话，只传接口定义、Bug 单、代码片段等结构化内容，限制最大交互轮次。

## 编码场景选型总结
| 编码任务复杂度 | 推荐架构层级 | 占比 | 典型产品/落地 |
| :--- | :--- | :--- | :--- |
| 单行/单函数修复、极简脚本 | L1 纯 ReAct | ~10% | 代码补全工具、轻量代码助手 |
| 单文件/单模块开发、单 Bug 修复 | L2 ReAct+SubAgent | ~70% | Cursor Agent、Claude Code、开源代码 Agent |
| 多文件/全栈功能、项目级重构 | L3 Planner+Executor | ~15% | Devin、企业级研发 Agent |
| 多角色团队协作、大型项目并行开发 | L4 受限混合架构 | <5% | 大厂内部研发智能体中台 |

## 落地建议
1. **优先从 L2 起步**：先跑通单文件读写+测试执行+调试闭环的基础编码 Agent，验证业务价值，90% 的日常场景都能覆盖。
2. **长任务痛点明确再升 L3**：当频繁出现“开发到一半跑偏”“多文件修改逻辑不一致”的问题时，再叠加 Planner 全局规划层，不要一开始就做重架构。
3. **L4 只做大客户增值**：不要面向全量用户开放横向协同能力，仅给企业级团队客户按需开通，且必须做严格的通信约束和隔离部署。


核心结论：**智能体中台不需要做两套独立系统，但必须在领域层做严格的场景化区分与隔离**。底层核心基座100%复用，上层领域Agent、工具权限、安全策略、算力配置按编码/办公拆分，是投入产出比最高的方案。

二者的差异不是「架构范式不同」（都适配L1-L4四层体系），而是**风险等级、工具权限、算力模型、审计规则、容错要求**存在本质区别，强行共用同一套执行配置，要么安全失控，要么成本浪费、体验不佳。

## 一、为什么必须区分：两大场景核心差异
| 对比维度 | 日常办公场景 | 编码研发场景 |
| :--- | :--- | :--- |
| **核心任务** | 信息查询、文档生成、流程审批、数据报表、客服答疑 | 代码编写、缺陷排查、重构优化、测试执行、依赖管理 |
| **安全风险等级** | 中低：主要风险是数据泄露、越权访问，不涉及系统底层操作 | 极高：可执行终端命令、读写文件、安装依赖，存在恶意代码执行、环境破坏风险 |
| **核心工具集** | OA/CRM/ERP接口、文档解析、知识库检索、审批流接口 | 文件读写、代码执行器、终端Shell、Git操作、依赖安装、静态扫描、单元测试 |
| **模型与算力** | 偏结构化、流程化，优先轻量模型降本，对上下文长度要求中等 | 强推理、长上下文，优先高性能模型，单任务Token消耗是办公的3~10倍 |
| **审计重点** | 敏感数据访问、操作留痕、审批链路合规 | 命令执行审计、文件变更溯源、沙箱操作全记录、代码风险扫描 |
| **容错率** | 较高：格式偏差、信息轻微遗漏可接受，流程正确即可 | 极低：语法错误、逻辑偏差直接导致功能失效，需要高频细粒度纠错 |
| **常用架构层级** | L1/L2为主，复杂流程用L3，极少需要L4 | L2为主力，项目级用L3，团队协作用L4 |

## 二、中台取舍原则：底座共用，领域隔离
中台的核心是「复用降本」，因此**通用能力全部下沉共用，场景差异化能力在领域层隔离**，既不重复建设，又满足各自的专业要求。

### 1. 100%共用的中台底座能力
这部分是中台的通用骨架，完全不需要做两套，对应L3及以下的基础能力：
- **租户与权限体系**：统一的租户隔离、角色权限、组织架构管理，BC两端共用
- **核心调度引擎**：Planner规划、DAG任务编排、重规划机制、任务状态管理完全通用
- **基础能力组件**：统一工具网关、RAG检索引擎、长时记忆系统、模型调度池、KV缓存
- **可观测与计量**：全链路Trace、日志审计底座、计费计量、异常告警框架
- **风控合规底座**：内容审核、敏感词过滤、数据脱敏基础能力

### 2. 必须场景化隔离的能力
这部分对应L2领域层、L1执行层的差异化配置，是区分的核心：
#### （1）工具集与权限边界隔离
- 办公场景：仅开放内部系统API、文档处理、知识库检索等「只读/轻写」工具，权限粒度到接口级别
- 编码场景：开放文件读写、Shell执行、依赖安装等高危工具，**必须运行在独立沙箱中**，权限粒度到目录、命令白名单，禁止越权访问办公数据

#### （2）运行环境与安全隔离
- 办公场景：仅需接口鉴权、数据脱敏，无需独立运行环境
- 编码场景：强制容器化沙箱隔离，每个任务独立环境，执行完毕可销毁，支持操作回滚，防止恶意代码污染主系统

#### （3）Agent与模型策略差异化
- 办公Agent：优先调用轻量模型，短上下文为主，提示词偏流程化、结构化，降低推理成本
- 编码Agent：优先调用强推理长上下文模型，提示词偏逻辑严谨、语法规范，配套代码校验、测试执行等专属纠错逻辑

#### （4）审计与风控规则差异化
- 办公场景：重点审计敏感数据导出、越权访问、审批操作
- 编码场景：重点审计高危命令执行、文件批量修改、外部依赖下载、代码安全漏洞

#### （5）容错与重规划策略差异化
- 办公场景：低频率重规划，以流程正确为核心，允许少量信息偏差
- 编码场景：高频细粒度重规划，单步执行失败立即重试/调整，语法、逻辑零容错

## 三、标准落地架构形态
在你之前梳理的四层中台架构基础上，仅需在**L2领域层做场景化集群拆分**，上层统一接入、下层共用底座，形态如下：

```
接入层：统一入口 + 场景路由（自动识别办公/编码任务）
    ↓
L3全局规划层：统一Planner调度引擎（共用）
    ↓ 分发任务
L2领域层：【办公领域Agent集群】  【编码领域Agent集群】（各自独立配置、工具、安全策略）
    ↓ 调用执行
L1原子执行层：通用工具网关 + 专属执行单元（办公API / 编码沙箱）
    ↓
统一底座：租户、计费、可观测、模型调度、RAG（共用）
```

### 关键落地规则
1. **能力订阅制**：租户按需订阅「办公能力包」「编码研发包」「全能力包」，不用全量开放，既控制风险又匹配计费
2. **跨场景通信默认关闭**：同场景内的Executor可开放受限横向通信（如编码的前后端Agent、办公的财务+人事Agent）；跨场景禁止直接互通，所有交互必须经顶层Planner中转，避免风险扩散
3. **算力池分层**：编码场景占用算力高、单任务耗时长，独立预留算力池；办公场景走共享算力池，避免编码长任务挤占办公轻量请求

## 四、隔离强度选型
不是所有中台都要做物理隔离，按规模和合规要求分级即可：
- **中小团队/中台初期**：逻辑隔离足够，通过「场景标签+权限规则+工具白名单」区分，研发成本最低
- **中大型企业/多租户中台**：沙箱环境隔离 + 算力池隔离，编码任务独立运行，保障主系统安全
- **强合规行业（金融/政企）**：物理集群隔离，编码环境与办公环境网络隔离，数据不互通，满足等保要求

## 总结
1. 架构范式上无需区分：编码和办公都适配L1-L4四层演进体系，共用同一套调度骨架
2. 执行层面必须区分：工具权限、安全环境、模型策略、审计规则差异极大，混跑必然出问题
3. 最优方案是「一个中台底座 + 多个领域集群」，通用能力复用、场景能力隔离，兼顾中台的复用性与场景的专业性，也是当前业界研发办公一体化智能体中台的标准落地方式。
